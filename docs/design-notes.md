# 設計メモ

gitlab-graph.user.js の実装で採用した設計判断と、その根拠になった調査結果をまとめる。

## 選択の滞在で詳細を先読みする

選択が同じコミットに 400ms とどまったら、詳細と diff をバックグラウンドで取得してキャッシュする。
j/k の連打中 (滞在 400ms 未満) はリクエストを一切発行しない。
取得中に展開された場合は同じ取得を待ち合わせるため、fetch は sha ごとに最大 1 回。
キャッシュは 50 件で頭打ちにし、挿入順の古いものから捨てる (展開中の sha は保護)。
sha に紐づく詳細は不変なので、リロードやブランチ切替での破棄はしない。

## same-origin の REST API v4 をセッション Cookie で叩く

グラフのデータは HTML のスクレイピングではなく `location.origin` の `/api/v4` から取る。
同一オリジンなのでブラウザのセッション Cookie がそのまま送られ、アクセストークンを持たせる必要がない。
トークンをスクリプトや設定に保存しないので、`@grant none` のまま動く。

| 用途 | エンドポイント |
|---|---|
| プロジェクト情報 (default_branch) | `GET /api/v4/projects/<enc>` |
| ブランチ一覧 (チップ・到達可能性) | `GET .../repository/branches?per_page=100&page=N` (最大 10 ページ) |
| ブランチ候補 | `GET .../repository/branches?per_page=100&search=<入力値>` |
| 幹の先端 | `GET .../repository/branches/<URL エンコードしたブランチ名>` |
| タグ | `GET .../repository/tags?per_page=100&page=N` (最大 10 ページ) |
| コミット (全ブランチ・初回) | `GET .../repository/commits?all=true&per_page=100` |
| コミット (全ブランチ・続き) | `GET .../repository/commits?all=true&per_page=100&until=<ISO日時>` |
| コミット (単一ブランチ) | `GET .../repository/commits?ref_name=<enc>&per_page=100&page=N` |
| コミット詳細 | `GET .../repository/commits/<sha>` |
| 変更ファイル | `GET .../repository/commits/<sha>/diff?per_page=100` |
| 作者アバター | `GET /api/v4/avatar?email=<email>&size=48` |

並び順を指定するパラメータはどのモードでも付けない。
後述のとおりクライアント側で必ず並べ直すため、サーバ側の並び替えに頼る必要がないから。

プロジェクトのフルパスは URL の `/-/` より前から取る (サブグループの階層数を固定で仮定しない)。
ref は `/-/network/` より後ろの全体を `decodeURIComponent` したもので、スラッシュで split しない (`feature/foo` のようにブランチ名自体がスラッシュを含むため)。
URL に ref が無いときは `default_branch` で埋める。

コミット詳細と diff は詳細パネルを開いたときに初めて取りに行き、sha ごとにキャッシュする。
応答を待つ間に別の行を開いていたら、遅れて届いた結果は捨てる。

## 全ブランチモードは page ではなく日時窓でさかのぼる

`all=true` を付けると `page` パラメータが無視され、`page=1` と `page=2` が完全に同じ 100 件を返す。
これは 2026-08-01 に gitlab.com の `gitlab-org/gitlab-foss` で curl 検証した事実。
一方で `until=<ISO日時>` は機能し、その日時以前の最新コミット群が `per_page` 件返る。
`ref_name=<branch>` を指定した場合は、通常どおり `page` ベースのページングが機能する (`page=1` と `page=2` で内容が異なる)。

そこで、コミットの取得はモードごとに戦略を分けている。

- **全ブランチ**: 初回は `until` なし。続きは「ロード済みで最も古い `committed_date`」を `until` に渡して次の窓を取る (日時窓チェーン)。
- **単一ブランチ**: `page` を 1 ずつ進める。

`until` は境界の日時を含むため、窓の境目のコミットは前後の窓の両方に現れる。
これは sha による重複除外でそのまま吸収し、境界がずれない (取りこぼさない) 側に倒している。

1 回の取得で新規の sha が 0 件だったら「これ以上さかのぼれない」と判断して打ち切り、その旨をツールバー下に表示する。
同一日時に 100 件を超えるコミットが固まっていると窓が前へ進まなくなるため、この打ち切りが無いと同じリクエストを永久に繰り返すことになる。

初期ロードは窓 3 回ぶん (最大およそ 300 件) を直列に取得する。
境界の重複ぶんだけ実際の件数は 300 件をわずかに下回る。
「さらに読み込む」と `l` キーは窓 1 回ぶん進める。

## コミット取得は世代単位で分離する

コミット取得を開始するときに、現在の mode / ref / `until` / `page` をその取得専用の値として固定する。ブランチを確定して再読み込みすると取得世代を進め、前の `AbortController` を中断する。遅いサーバや AbortSignal を無視する fetch 実装から旧応答が返っても、応答適用時の世代が一致しなければ state へ追加しない。これにより、全ブランチ取得中に単一ブランチへ切り替えても旧コミットや旧ページ番号が混ざらない。

## API の並びを信用せず、自前でトポロジカルソートする

commits API の並びは「子が親より必ず先」を保証しない。
2026-08-01 に gitlab.com で実測した事実として、窓の中が昇順 (古い順) で返る例を観測している。
そもそも日時窓を継ぎ足して 1 つのウィンドウを作る以上、窓をまたいだ並びがトポロジカルになる保証は無い。

そのため API の並びは表示順として採用せず、ロード済みのコミット全体をクライアント側で並べ直す。
sha → commit の Map を作り、「ウィンドウ内に子を持たないコミット」を起点に Kahn 法でトポロジカルソートする。
同時に ready になったコミットは committed_date の降順で先に出す (同時刻は sha で決定的に並べる)。
Map に無い親 (= ロード済みウィンドウの外) は辺として数えない。
ready 集合はこの比較順を優先度にした二分ヒープで管理し、出力順を保ったまま追加・取り出しを `O(log n)` にしている。

「さらに読み込む」で追記したあとは、ウィンドウ全体で並べ直す。
そのため既に表示されていた行の並びやレーン位置が、追加ロードで変わることがある。

## MR の一時 ref (テストマージ) を除外する

`all=true` は「リポジトリの全コミット」を返すため、GitLab が MR ごとに内部生成する一時 ref のコミットも混ざる。
`refs/merge-requests/<N>/merge` (merged results パイプライン用のテストマージ) がこれで、どのブランチにも属さない先端として現れる。

2026-08-01 に `gitlab-org/gitlab-development-kit` で実測した。
階段状に並んでいた「Merge branch 'X' into 'main'」6 件 (`48fcbe26` / `19b96c87` / `fc81d4e7` / `82a0d4cf` / `7913adb6` / `e16e88cf`) は、いずれも `ref_name=main` の履歴に含まれていなかった = main から到達できない。
同じタイトルのマージが 2 つ並ぶ現象 (`renovate/rust-1.x` など) も、本物とテストマージの両方が返っていると考えれば整合する。
ユーザー報告の「マージコミットがマージ先ブランチに合流せず宙ぶらりん」は、実ブランチのマージではなくこのファントムだった。

そこで全ブランチ表示では、既知の ref から到達できるコミットだけを表示する。

- 起点は「最大 10 ページまで読み切った branches 一覧のブランチ先端」∪「同じく tags 一覧のタグ先端」∪「幹の先端」。
- 起点から `parent_ids` を辿って到達集合を作り、そこに入らないコミットを表示から外す。
- branches / tags の両方を最終ページまで取得できた場合だけフィルタする。一覧 API の失敗、または 10 ページ目も 100 件で続きの有無を確定できない場合は fail-open で自動無効化し、理由をステータス行へ表示する。
- 起点の材料はコミット取得と並行で取得し、完全性が確定するまでは暫定的に全件表示する。
- 単一ブランチ表示では適用しない (サーバ側がその ref の履歴しか返さないため)。
- ツールバーのチェックボックスで OFF にすれば従来どおり全件表示になる (既定 ON、localStorage に保存)。

ファントムは大量のレーンを占有するため、除外するとレーン数が大きく減り、`(+N)` の切り詰めも起きにくくなる。

## 幹 (mainline) に専用レーンを与える

表示中の ref の先端から第 1 親をたどった連なりを「幹」とし、レーン 0 を予約して他のブランチに使わせない。

これが無いと、bot が作った大量のブランチ先端 (renovate 系など) が左のレーンを先に埋めてしまい、幹のレーンが行ごとに入れ替わる。
その結果、連続するマージコミットが繋がって見えず「宙ぶらりん」になり、階段状に右へ散っていく。
2026-08-01 に gitlab.com の `gitlab-org/gitlab-development-kit` の `/-/network/main` (全ブランチ表示) で観測した。

幹の先端 sha は **ブランチ 1 本を名前で引くエンドポイント**から取る。

```
GET /api/v4/projects/<enc>/repository/branches/<URL エンコードしたブランチ名>
```

引くブランチは、単一ブランチ表示ならそのブランチ、全ブランチ表示なら default branch (プロジェクト情報の `default_branch`)。
ブランチ名にスラッシュが入るので `encodeURIComponent` は必須。

一覧 (`/repository/branches?per_page=100`) から探してはいけない。
一覧はアルファベット順の 100 件しか返らないため、数字始まりや `a` 〜 のブランチが 100 件以上あるリポジトリでは default branch が 1 ページ目に入らない。
`gitlab-org/gitlab-development-kit` では実際に `main` が 1 ページ目に無く、一覧から探す実装では幹の予約が発動しなかった (2026-08-01 に curl で確認)。

この取得は再読み込みごとに 1 回。コミット取得と並行して投げ、遅れて届いた場合はレーンを組み直す。
取得が失敗した場合 (404 など) や先端がウィンドウ内に無い場合は幹なしで動き、代わりに「同じコミットを複数のレーンが期待しているときは、最も長く続いている線を残す」規則でレーンの安定を保つ。
このフォールバックでは、幹の線が最初の衝突で 1 度だけ隣のレーンへ移ることがある (そこから先は動かない)。
どちらの経路でも、短命ブランチのほうが幹のレーンを奪い続けることはない。

## レーン割り当て (Git Graph 方式)

`lanes[]` (各レーンが次に期待する sha) を保ち、トポ順に 1 行ずつ処理する。

1. この commit の sha を期待しているレーンを探す。無ければ左端の空きレーンを新規確保する (ブランチ先端)。commit のレーンは期待レーン群の最左。
2. 期待していた他のレーンは commit のドットへカーブして合流し、解放される。
3. commit のレーンは第 1 親の sha を期待するようになる。親が無ければレーンを閉じる。
4. マージコミットの第 2 親以降は、その sha を既に期待しているレーンがあればそこへカーブ接続し、無ければ空きレーンを新規確保して期待させる。

同じ行で解放したレーンは、その行の分岐先として再利用しない。
合流のカーブと分岐のカーブが同じ x で重なって読めなくなるのを避けるため。

ウィンドウ外の親を期待したままのレーンは最後まで埋まらないので、線がテーブル下端まで伸びる。
これは「まだ読み込んでいない先がある」ことを示す表示として意図している。

## ブランチ選択は select ではなく datalist にする

branches API はブランチ名のアルファベット順でしか返らず、並び替えのパラメータが無い。
ブランチが数千あるリポジトリでは 1 ページ目 (100 件) が `10-0-stable`, `10-1-stable`, … で埋まり、default branch の `master` すら候補に現れない。
2026-08-01 に gitlab.com の `gitlab-org/gitlab-foss` で確認した。

そこでブランチ選択は `<select>` をやめ、`<input list>` + `<datalist>` のコンボボックスにしている。

- 入力を 250ms デバウンスして `search=<入力値>` 付きで候補を取り直す。サーバ側の絞り込みなので、100 件を超えるリポジトリでも任意のブランチに到達できる。
- default branch と URL の ref は候補の先頭に常にピン留めする (重複する場合は 1 つ)。
- 候補の検索ではコミット一覧を取り直さない。取り直すのは確定時 (datalist からの選択・Enter・編集後の blur による change) だけ。同じ値での再確定は無視する。
- Enter の確定判定には IME ガード (`isComposing` / `keyCode === 229`) を入れてある。変換確定の Enter でブランチが切り替わらないようにするため。
- 確定したら入力欄を blur する。フォーカスが残っていると、続けて押した `j` / `k` がブランチ名の続きとして入力され、次の Enter で存在しないブランチとして確定されてしまう (2026-08-01 に gitlab.com で踏んだ)。
- 存在しないブランチ名で確定された場合は握りつぶさず、ツールバーの下にエラー行を出す。

存在しない `ref_name` に対して、commits API が 404 ではなく **200 + 空配列** を返すことがある。
2026-08-01 に gitlab.com の `gitlab-foss` で「存在しないブランチを確定したのに 0 行になるだけでエラーが出ない」状態を踏んだ。
HTTP エラーが起きていないので当然エラー行も出ず、綴り間違いに気づけない。
そのため ref_name モードでロードが終わって 0 件かつエラーも無い場合は、「ブランチ名が正しいか、アクセス権があるか確認」というエラー行を自前で追加している。

件数表示は `<スコープ>: 表示 N 件 / 読み込み済み M 件` の形にし、`(全件)` は「1 件以上読めていて、エラーが無く、続きも無い」ときだけ付ける。
取得に失敗した 0 件を `(全件)` と表示すると、成功して 0 件だったのと見分けが付かないため。

チップ用のブランチ一覧 (`state.branches`) と候補用の一覧 (`state.branchOptions`) は分けてある。
候補を検索で絞り込んでも、行に付くブランチチップが消えないようにするため。
初期候補は従来どおり 1 ページ目だけを使い、それを超える名前は入力時のサーバ側検索で探す。到達可能性とチップに使う一覧をページングしても datalist が最大 1000 件へ膨らまないよう分離している。

## Graph 列の幅を頭打ちにする

bot が単発コミットのブランチを大量に作るリポジトリでは、300 件のウィンドウ内で同時レーン数が数十〜数百に達する。
2026-08-01 に gitlab.com の `gitlab-org/gitlab-foss` (`/-/network/master`、全ブランチモード) で確認した。
レーン数のぶんだけ Graph 列を伸ばすと、列がビューポートのほぼ全幅を占有し、コミットタイトルが画面外へ押し出されて読めなくなる。

そこで描画するレーン数に上限 (16 本) を設けた。

- Graph 列の幅は `min(ウィンドウ内の最大レーン数, 16) × 14px + 余白` で、再描画のたびに `colgroup` の `col` へ px で書き込む。下限は 56px (0 行のときでも `GRAPH` ヘッダが収まる幅)。
- ヘッダのセルは `overflow: hidden` + ellipsis。列が狭くなっても隣のヘッダに文字が重ならないようにする。
- 上限を超えたレーンは SVG の外に出て、`overflow: hidden` でクリップされる。
- 切り詰めているあいだは列の右端に背景色へのフェードをかけ、続きがあることを示す。
- ヘッダに `(+N)` で隠れているレーン数を出す。ツールチップに実際のレーン総数を入れる。
- 上限より右のレーンにいるコミットは、ドットだけ最右のレーンに寄せて描く。切り落とすと行からドットが消えて「どのコミットが表示外なのか」すら分からなくなるため。寄せたドットにはレーン番号のツールチップを付ける。

列レイアウトは `table-layout: fixed` + `colgroup` で固定し、Description 列だけ幅を指定せず残り幅を全部取らせる。
Author (160px) / Date (130px) / SHA (86px) は固定幅。
テーブルには `min-width` を切ってあり、狭いビューポートではタイトル列を潰さずに横スクロールさせる。
詳細パネルの行も同じ `colgroup` に従い、パネル本体は Description 以右の 4 列ぶんを使う。

## アバターは email 単位で遅延取得する

アバターの URL は `GET /api/v4/avatar?email=<email>&size=48` が返す `avatar_url` を使う。
GitLab 自身がアバター解決に使っているエンドポイントで、プロジェクト配下ではなく認証も不要。
返る URL は Gravatar のような外部ホストになることもあるが、GitLab のページ自身が同じ URL を `<img>` で読んでいるため、ページの CSP と衝突しない。

取得はコミット単位ではなく **email 単位**で、同時 4 件までに絞って遅延実行する。
結果 (失敗も含む) は email ごとにメモリキャッシュし、同じ email を二度取りに行かない。
取得前・取得失敗・画像の読み込み失敗のときは、email のハッシュから決めた色に名前の頭文字を載せた円を出す。
色は email から決まるので、同じ人はどの行でも同じ色になる。
`<img>` には `loading="lazy"` と `alt` を付け、大きさは 20px 固定にして行の高さ 26px を崩さない。
アバターが出ないだけではエラー行を出さない (グラフの読み取りに影響しないため)。

## 変更ファイルから diff へ直接飛ぶ

詳細パネルの変更ファイル一覧は、GitLab のコミットページの該当 diff へのリンクにしている。

```
<コミットの web_url>?file_path=<encodeURIComponent(new_path)>#<new_path の SHA-1 (hex)>
```

アンカーの 40 桁 hex がファイルパスの SHA-1 であることは 2026-08-01 に gitlab.com で確認した (`.gitignore` → `a5cc2925ca8258af241be7e5b0381edf30266302`)。
SHA-1 は `crypto.subtle.digest("SHA-1", ...)` で計算する。非同期なので、まず `?file_path=` 付きの href でリンクを作り、ハッシュが求まってからアンカーを足す。
`crypto.subtle` は secure context 専用なので、使えない環境ではアンカー無し (`?file_path=` だけ) にフォールバックする。
リンク先には常に `new_path` を使う (削除されたファイルでも `new_path` に同じパスが入る)。

## 全幅表示とネイティブ表示の永続化

「全幅」は `html` に `glg-full-width` クラスを付け、GitLab のコンテンツ幅制限を CSS で外す。
クラス名は世代によって変わるため、既知の名前 (`container-limited` / `limit-container-width` / `gl-container-limited`) と `[class*="container-limited"]` のような部分一致の両方を狙って `max-width: none` を当てている。
元からフルード幅のレイアウトでは当たる要素が無く、実質何も起きない。

表示モードと全幅設定は localStorage に保存する (`glg-view-mode` = `custom` | `native`、`glg-full-width` = `1` | `0`)。
localStorage はプライベートモードなどで例外を投げることがあるので、読み書きはどちらも失敗を握って続行する (保存できなくても機能自体は動く)。
ネイティブ表示中は自前のツールバーごと隠れて戻る導線が無くなるため、`.project-network` の直前に「カスタム表示 (gitlab-graph) に戻す」ボタンを常に置いている。

## 行単位の小さな SVG を積む

グラフは 1 枚の巨大な SVG ではなく、行ごとに独立した小さい SVG セルとして描く。
詳細パネルのインライン展開で行の高さが可変になるため、行単位なら展開のたびに全体を描き直さずに済むという判断。
詳細パネルの行にも「通過中のレーンの縦線だけ」を描いた SVG を置き、線の連続性を保つ。
この縦線は `height="100%"` の `rect` で描いており、パネルの高さが変わっても線幅が歪まない。
`rect` の中心 (`x + width / 2`) は通常行の `line` の中心 (`x1`) と一致させる。線の太さは両者で同じ定数を使う。

レーンをまたぐ遷移 (合流・分岐・隣接行のドット間のレーン移動) は、**遷移元の行の中心から遷移先の行の中心まで 1 行ぶん (26px) を使う大きな S 字**で描く。
VS Code の Git Graph 拡張と同じスパンで、半行 (13px) に押し込めると通常倍率ではほぼ直角に見えてしまうため。
全体カーブは `M x0 0 C x0 H/2, x1 H/2, x1 H` (`H` = 行の高さ)。制御点の x が両端と同じなので両端の接線が垂直になり、上下の縦線と折れ目なく繋がる。

行の境界をまたぐので、De Casteljau で `t = 0.5` に分割して上下 2 行の SVG に半分ずつ描く。

- 上半分 (上側の行の下半分セル): `(x0, 0)` `(x0, H/4)` `((3x0+x1)/4, 3H/8)` `((x0+x1)/2, H/2)`
- 下半分 (下側の行の上半分セル): `((x0+x1)/2, H/2)` `((x0+3x1)/4, 5H/8)` `(x1, 3H/4)` `(x1, H)`

分割点は必ず `((x0+x1)/2, H/2)` で、両半分の接線ベクトルはどちらも `((x1-x0)/4, H/8)` なので繋ぎ目に折れは出ない (C1 連続)。
遷移が占める半セルでは、そのレーンの縦線を描かない (縦線とカーブの二重描画を防ぐ)。
ウィンドウの先頭行への合流・最終行からの分岐など隣の行が無い場合は、半行に収めた小さい S 字にフォールバックする。
詳細パネルが遷移境界を挟む場合は、上側の行内で `halfRowPath` により行き先レーンまで遷移を完了させる。ガターは行き先レーン中心の縦線、下側の行は同じ x の上半分縦線に組み替えるため、分割点が別レーン中心と一致して 2 本が完全に重なることはない。パネルを閉じた場合と、パネルが挟まっていない境界は通常の De Casteljau 分割のままにする。
`fill="none"` を忘れると path が塗り潰される。

グラフのセルの `padding: 0` は、`.glg-table td { padding: 0 8px }` に詳細度で負けないよう `td` を含めた選択子で書く。
負けると、通常行の SVG は左 padding の後ろから流れる一方、詳細行の SVG は絶対配置で padding box の左端に貼り付くため、**詳細行の縦線だけが 8px 左にずれる**。
コミットを選ぶと詳細パネルが開くので「選択するとグラフのインデントがずれる」という形で現れた (2026-08-01 に gitlab.com と GitLab 17.5 の CSS を使ったローカル再現の両方で確認)。

## `.project-network` を隠して差し替える

ネイティブのグラフページは Vue で描かれるため、`.project-network` が現れるまで MutationObserver で待つ (10 秒でタイムアウト)。
タイムアウトした場合は何もせず、ネイティブ表示のまま放置する。

乗っ取りは `.project-network` に `display: none` の class を付け、その直後に自前のルート要素を挿入する方式にしている。
DOM を削除しないので、ツールバーのトグルで即座に元の表示へ戻せる。

GitLab 17.5 系では、ネイティブの ref 切替 (`#js-graph-ref-switcher`) と英語の説明行 (`.oneline`) が `.project-network` の**外 (前)** にある `.row-content-block` に入っている (`app/views/projects/network/_head.html.haml`)。
そのままだと自前 UI の上に残るので、`#js-graph-ref-switcher` が存在すれば `closest(".row-content-block")` をカスタム表示中だけ隠し、ネイティブ表示に戻すときは元に戻す。
現行の gitlab.com にはこの要素が無く、存在チェックで自然に no-op になる。

この方式は GitLab 側の DOM 構造に依存しており、`.project-network` という class 名が変わると乗っ取りが成立しなくなる。
その場合はスクリプトが何もしないだけで、ネイティブのグラフはそのまま表示される (壊れた画面にはならない) という設計にしている。
class 名に依存するのは、このページに `data-testid` 相当の安定した手がかりが見当たらなかったため (2026-08-01 時点の gitlab.com で確認)。

## スタイルは全部注入・`glg-` プレフィックス

CSS は `<style>` で注入し、class 名は `glg-` で始める。
配色は CSS 変数にまとめ、GitLab のダークモード (`body` または `html` の `gl-dark` class) で切り替える。
自前のサブツリーにしか当たらない選択子なので、非表示の強制以外に `!important` は使っていない。

## 診断方法

開発者ツールの Console で `console.table({...document.documentElement.dataset})` を実行すると、`glgVersion` / `glgMode` / `glgRef` / `glgLoaded` / `glgVisible` / `glgHidden` / `glgLanes` / `glgGeneration` / `glgLastError` を確認できる。各値は通常の再描画経路で常時更新され、`glgLastError` は最後のエラーソース名 (エラーなしなら空文字) になる。
